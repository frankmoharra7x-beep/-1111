设计说明 · 为什么是「滑轨当第 7 轴」

Airport Baggage Robotic Loading Simulator · 竞赛答辩用

0. 一句话论点

把直线滑轨沿机身纵深方向铺在集装箱中线上，让机械臂像进隧道一样开进 ULD 内部作业， 把"从舱外一次性伸到舱内最远端"的三维大臂展需求， 降维成"滑轨纵向定位 + 短臂横向微操"的两个低难度子问题。

1. 降维：2.2 m 臂展 → 1.44 m 臂展

若无滑轨，机械臂只能固定在舱外（门口）基座。以本算例 LD3 尺寸（1534×1562×1626）为例， 取基座在门口中心、肩部铰点高 600 mm、末端工具 180 mm，要把行李送到舱内最远的上层角落 （约 x=1031, y=1500, z=1626），所需腕点半径约

D ≈ hypot( |1031−767|, |1500−0|, (1626+180)−600 ) ≈ 2.0 m  →  工程选型通常按 2.2~2.5 m 臂展

加了滑轨之后，滑台可以直接停在目标所在的工位（纵向偏差 ≤ 步长/2 = 200 mm）， 机械臂只需覆盖横向半宽 767 mm + 纵向残余 200 mm + 高度，腕点半径降到

D ≈ hypot( 767, 200, 1206 ) ≈ 1.44 m  ≤  L1+L2 = 760+680 = 1440 mm

结论：臂展需求下降约 35%。对大一团队而言，这意味着可以用更小、更便宜、 更轻、刚性更好的机械臂，同时末端挠度（臂越长挠度越大，直接恶化放置精度）显著改善。

2. 坐标系约定（严格沿用算法原文件）

符号含义范围
x宽度方向（左右）[0, W=1534]
y纵深 / 机身方向，舱门在 y=0 端[0, D=1562]
z高度方向[0, H=1626]
  • 单位 mm，行李坐标一律取最小角点（min-corner），与 placement.x/y/z 完全一致。
  • Three.js 是 Y-up 右手系，映射关系为 Three(X, Y, Z) = (x, z, −y)（行列式 = +1，是真旋转，不是镜像）。
  • 绕竖直轴 yaw 在两套坐标系下角速度相同、符号相同，因此 J6 可直接用于 Three 的 rotation.y。

3. 逆运动学（解析解，不依赖场景图层级）

正解（给定 railY 与 J1..J6）：

S = (767, railY, 250+350) = (767, railY, 600)
E = S + u·L1·cos J2 + ẑ·L1·sin J2
Wr = E + u·L2·cos(J2+J3) + ẑ·L2·sin(J2+J3)
TCP = Wr − ẑ·dTool

逆解（给定 TCP 目标 P）：

dx = px−767, dy = py−railY, r = hypot(dx,dy), s = (pz+dTool)−600
J1 = atan2(dy, dx),   D = hypot(r, s)
α = acos( (L1²+D²−L2²) / (2·L1·D) ),   β = atan2(s, r)
J2 = β + α,   θ = acos( (L1²+L2²−D²) / (2·L1·L2) )
J3 = θ − π,   J5 = −π/2 − (J2+J3),   J4 = 0

关键恒等式：J2 + J3 + J5 ≡ −π/2，这保证末端工具恒指向正下方， 从而"姿态"这一维度被结构性地解耦掉——位置逆解不需要迭代，一次代数运算即可完成。

可达性判据：|L1−L2|+1 ≤ D ≤ L1+L2−1； 关节限位：J2 ∈ [−95°, +150°]、J3 ∈ [−150°, 0°]（肘部上弯构型）。

4. 算法 → 机构：完整数据流

5. 工位规划：滑轨不只是"加长臂展"，更是"规避死区"

  • 开启工位批处理（默认）：步长 STATION_STEP = 400 mm，工位 Y = round(py/400)·400，并 clamp 到 [0, D]。一个工位服务多个相邻目标，此时 dy ≠ 0，J1 会真实变化，画面上能看到机械臂"转身"。
  • 若某目标在该工位逆解不可达 → 降级为逐件定位 railY = clamp(py, 0, D)（dy = 0）。
  • 若 dy = 0 仍不可达 → 沿 Y 以 50 mm 步长双向外扩搜索最近的可达工位。

为什么最后一步不可省（本项目实测得出的结论）：直觉上"把滑台停在行李正上方、dy = 0"应该最容易够到， 但对 6 轴臂恰恰相反。肘关节限位 J3 ≥ −150° 等价于要求肘部张角 θ ≥ 30°， 由余弦定理反解出腕点到肩部的最小可达距离

Dmin = √( L1² + L2² − 2·L1·L2·cos30° ) ≈ 380.6 mm

也就是说肩关节周围存在一个半径约 381 mm 的球形折叠死区：臂杆再长也伸不进去， 因为肘部折不动。地板层行李的顶面中心往往只比肩部低 180~360 mm，水平偏移又不足 381 mm， 正好落进死区。此时把滑台沿 Y 推开，反而能拉大水平臂展 r、让手臂展开并满足限位。 本算例 28 件中有 8 件需要这一步，平均工位偏移约 250 mm。

这条论据比"降维"更有说服力：即便臂展已经足够，没有第七轴仍然装不满一个 ULD。 仿真会在日志中输出每一件的 stationOffset（工位偏移）与 reachSlack（可达性裕度），可直接引用。

5b. 可达性裕度：为什么规划与执行要用不同的余量

工位筛选要求 slack ≥ 50 mm，而执行期只要求 slack ≥ 10 mm。 两者必须错开一档：末端重复定位误差（σ≈1 mm）会让实际目标点偏离名义值约 1 mm， 若两处用同一个阈值，"刚好够得着"的工位就会在执行时被判为不可达（实测约 1% 概率/件，28 件下几乎必现）。 slack 的定义也必须与 ik(margin) 的判据严格等价（含那 1 mm 的硬裕度）， 否则会出现"规划通过、执行失败"的自相矛盾。

6. 一个"巧合"的工程价值

算法原文件里 assignSequence() 的排序是先按 z 分层（低层先装）、层内按 y 降序（远端优先）， 这个顺序本来是为了"像人一样码放"。而对本机器人系统，它恰好等价于 "滑轨先深入舱内最远端，再逐件向外退装"—— 即天然避免了"先装外圈挡住内圈"的干涉，也天然缩短了滑轨的空行程。 这是算法层与机构层目标函数一致的一个巧合，值得在答辩中点出来。

7. 工程局限（务必在答辩中主动说明）

  • 未做动力学：所有运动按 smoothstep 位置插值，节拍由"行程 ÷ 额定速度"估算，未建模惯量、加减速、振动与末端挠度。
  • 未做真实视觉伺服：行李尺寸/位姿在本仿真中直接来自算法批次的名义值；界面中标注"视觉系统给出尺寸/位姿"仅表示信息来源，未实现图像处理或位姿估计误差传播。
  • 避障是简化的：只做"已放置行李 vs 搬运行李"的 AABB 检测与安全通道高度约束；未做机械臂连杆本体的避障、未做 ULD 壁面/门框的干涉检查。
  • 非实机：本系统是仿真演示，不含真实 PLC/驱动器接口、安全回路、急停与风险评估，不可直接用于真实机场作业。
  • 抓取模型简化：假设平行夹爪对被抓件成立（刚性、摩擦足够、重心在夹取点附近），未校核夹持力与滑移。

8. 统计口径（全部来自实际运行）

  • 滑轨累计行程 / TCP 轨迹长度：主循环每帧对 |ΔrailY| 与 |ΔTCP| 做数值积分。
  • 单件节拍：该件从 S0 起到 S9 止实际消耗的仿真时间（含异常处理）。
  • 放置误差：释放瞬间 |实际 min 角点 − 算法目标 min 角点| 的三维欧氏距离。
  • 体积 / 载重利用率：用实际已放置件的体积和与重量和除以 BP.containerVolume() 与限重，不是照抄求解器 metrics。
  • 页面在仿真未开始时所有统计显示 --；不存在任何写死的结果数值。
